# Private cancellable transport foundation

This is an unactivated Rust transport increment for EW-22. It has no public command, coordinator caller, canonical write, live receipt format or UI. The existing direct collector still follows its existing synchronous path, and the durable collection records remain synthetic-only. These tests establish neither live collection cancellation nor an approved release.

The crate-private `fetch` accepts the existing `RequestTicket`, normalized selected `CollectionInput`, an execution window, an earliest permitted start instant and a cancellation token. The later coordinator must obtain the ticket from the committed reserve-before-request operation. This transport cannot authenticate a ticket against SQLite and must not become a public arbitrary-URL entry point. It returns an observation; it does not publish evidence or alter request accounting.

## One owned operation

One process-wide mutex admits at most one call to the new production entry point. A competing call returns `Busy` without resolving or sending. A poisoned gate or an unverified resolver stop refuses subsequent calls with `RecoveryRequired`; there is no reset API. Native resolver helpers and endpoint configuration are private. The synthetic tests can inject a resolver and loopback endpoint only through code compiled under `cfg(test)`.

The HTTP stage uses a dedicated, single-thread Tokio runtime and an asynchronous reqwest client. Its future stays pinned across short cancellation polls; polling timeout does not restart a request. On return, the response, client and dedicated runtime are dropped before a local-operation-ended result escapes. There is no subprocess, detached task, `spawn_blocking`, default getaddrinfo fallback or independently operated service. The existing locked Tokio and rustls packages are reused; the lockfile adds direct workbench-core dependency edges without introducing a resolved package or version.

`locally_quiescent` concerns resources owned by this operation. It never means a remote server received nothing, a shared DNS daemon stopped all activity, or a request can be uncharged. The future coordinator must retain unresolved reservations as charged unknown outcomes. A completed body that races cancellation/deadline remains complete bytes with a separate `stop_observed` reason; it must not erase either observation.

## Destination and response rules

The existing collection input and destination validators enforce credential-free canonical HTTPS URLs on port 443 and exact analyst-selected hosts. Each operation observes at most 64 address candidates and rejects the entire observed set if any address is unsafe, including private, local, link-local or mapped loopback addresses. Only those validated addresses reach the connector. Subsequent DNS rebinding cannot change this request's pinned set; an unexpected resolver name fails. A successful response must report a remote socket within the pinned set.

The client keeps certificate and hostname verification enabled, disables environment/system proxies, automatic redirects, retries, referer and connection pooling, and requests HTTP/1 with identity content encoding. It sends fixed Accept and User-Agent fields and no case contents, cookies or credentials. TCP connection attempts may try another address within the pinned snapshot; no new address lookup or HTTP request retry is enabled. A redirect is returned as bounded, validated HTTPS metadata, never followed here. Selected-host permission, robots state, per-host pacing and charging for the next hop remain the canonical scheduler's responsibility.

A single complete body is at most the existing 2 MiB `PAGE_BYTES` limit. Declared oversize fails before collecting it; incremental chunk accumulation also stops at the limit. Empty, error and redirect bodies are retained as complete bytes when EOF is observed. Failed, cancelled, oversized or truncated bodies return no body and no invented original hash. Non-identity encoding is flagged and never decoded here; its complete raw bytes remain available for the existing non-indexed retention rules. Content metadata is not a statement of source truth or accepted extraction quality.

## Clocks and cancellation

`ExecutionWindow` keeps the canonical first-start wall deadline and last observed wall time supplied by the eventual owner, plus a monotonic deadline for this execution segment. The remaining segment may not exceed 600 seconds. Backward wall time fails explicitly; forward deadline expiry also stops. Resume must derive a segment from the original persisted deadline rather than reset it. Transport observations retain the exact final wall sample that was checked, including a backward sample; a second unvalidated clock read cannot replace it. Elapsed and wall values are not clamped into validity.

Cancellation, pacing and async waits check at intervals of at most 20 ms when the operating system and executor are scheduled. DNS has a five-second stage deadline; connect/TLS is bounded to five seconds, and headers plus body to fifteen seconds, all capped by the remaining segment. These are cooperative observation bounds, not a hard real-time or kernel resource quota. Trusted OS calls, including DNSService creation, ProcessResult and deallocation, plus Winsock startup, resolver, cancellation and result/free calls, cannot be forcibly preempted by this implementation. No native cancellation-latency claim follows from the local fixture tests.

## Native resolver contracts

On macOS, a narrow DNSService subscription requests both address families. `MoreComing` marks batching, not completion of all possible answers; callbacks may subsequently add or remove addresses. This implementation accepts the bounded batch it actually observed, records `macos_dns_service_observed_batch` and sets `authoritative_complete_set` to false. Every observed address, including a removal notification, is policy checked. A maximum of 256 callbacks prevents unbounded application-side accumulation. Polling and `DNSServiceProcessResult` run on one serialized context; the subscription is deallocated there before callback storage is released or candidates returned. It makes no claim that mDNSResponder has ceased unrelated or shared work. See Apple's [DNSService API contract](https://github.com/apple-oss-distributions/mDNSResponder/blob/main/mDNSShared/dns_sd.h), including MoreComing and the thread-safety/deallocation notes. The implementation was also checked against the installed macOS SDK header and links the system DNSService re-export through libSystem.

On Windows, `GetAddrInfoExW` uses DNS namespace only, an owned manual-reset event and stable caller allocations. Initial `WSA_IO_PENDING` (997) keeps those allocations alive. `GetAddrInfoExOverlappedResult` documents `WSAEINPROGRESS` (10036) while pending; 996 and 997 are conservatively treated as pending too. Neither a signalled event alone nor a successful cancel call frees the context. A terminal completion permits freeing caller-owned results/event/storage. See Microsoft's [GetAddrInfoExW](https://learn.microsoft.com/en-us/windows/win32/api/ws2tcpip/nf-ws2tcpip-getaddrinfoexw) and [overlapped-result contract](https://learn.microsoft.com/en-us/windows/win32/api/ws2tcpip/nf-ws2tcpip-getaddrinfoexoverlappedresult).

Microsoft documents that synchronous namespace-provider work can continue after cancellation. `WSA_E_CANCELLED` (10111) or a completion after our cancellation request therefore returns `QuiescenceUnverified`, with `ReleasedAfterCompletion` describing only the caller storage. If completion remains unconfirmed after a one-second cleanup wait, or waiting fails, the operation is deliberately retained with `RetainedPendingCompletion`. Both paths quarantine the new transport process; no further resolver or HTTP request starts through it. A cancel return such as `WSA_INVALID_HANDLE` cannot establish completion. See the [GetAddrInfoExCancel contract](https://learn.microsoft.com/en-us/windows/win32/api/ws2tcpip/nf-ws2tcpip-getaddrinfoexcancel).

This bounds retained application contexts to one failed operation in this new transport lane. Retained storage lasts until process exit and is never silently reused. A future activation must route all collection execution through this guard and persist a recovery-required state; it must not leave an alternate synchronous path able to bypass quarantine. Shared OS/provider resource use is not an application-enforceable bound. Actual Windows completion, cancellation, handle lifetime and recovery behaviour remain unverified on native Windows.

## Synthetic verification and remaining integration

Rust tests bind ephemeral loopback sockets with a synthetic TLS identity for `collection.invalid`. A private test-only endpoint maps a synthetic validated address to that listener and adds a fixture CA to that one client. The ordinary destination policy still rejects loopback before the override. No public DNS or HTTP request is made by this suite. The fixture CA is never installed in an OS trust store. An untrusted CA and wrong hostname must fail before HTTP is observed.

The tests cover selected-host refusal, mixed/private/mapped candidates, candidate limits, cancellation before launch/during pacing/resolution/TLS/header/body waits, owned socket closure, exact empty/error/redirect/encoded bodies, exact 2 MiB acceptance and oversized/chunked/truncated refusal, no automatic redirect or send retry, complete-body/cancellation races, wall rollback/monotonic expiry, unexpected resolver names, macOS callback batches and bounded callback counts. Windows pending return codes and both uncertainty-lifetime outcomes have platform-independent tests; those tests do not execute Windows DNS. A standalone Windows-target type check compiles the actual resolver FFI source against locked windows-sys with minimal type-only surrounding stubs. It checks signatures, not linking, OS behaviour or a complete Windows core build.

The verification record is [verification/cancellable-transport.json](verification/cancellable-transport.json). Earlier compile, linker and fixture synchronization failures are retained there. This source increment does not change public schemas, existing collector behaviour, canonical storage, report history or UI.

Required follow-up remains: integrate the single canonical coordinator owner; atomically reserve before dispatch; checkpoint complete responses through existing shared retention/extraction rules; join cancellation before publication; persist unknown completion/recovery states; preserve exact robots/redirect ancestry and the original deadline across restart; add public typed progress/receipt schemas and disclosure preview; prove actual native platform shutdown; then perform an explicitly authorized harmless live selected-site observation. No hosted search provider, account, key, unrestricted downloaded adapter or external server is introduced. Access approval, relevance assessment and the broad-discovery benchmark remain separate gates.
