# Durable collection foundation (EW-22)

This increment implements a **private, synthetic-only** Rust state machine and canonical storage operations. It adds no command, published JSON schema, live transport, background executor or UI control. The existing direct collector remains synchronous. No complete-release gate passes as a result of these tests, and this increment does not establish cancellable DNS, TLS or response reads.

The new record format is independently versioned as `schema_version: 1`, with collector policy `direct-https-durable-foundation-v1`. It requires `synthetic: true`; it cannot represent an actual live acquisition. All entry points are crate-private, and currently unreachable from application dispatch. The deliberate dead-code allowances are limited to these unactivated modules. Public activation, source-build identity and a live receipt contract require a further reviewed increment.

## Canonical model and checkpoints

`collection_jobs.rs` defines strict inputs, events, checkpoints, charged requests and private execution tickets. `collection_machine.rs` applies deterministic transitions without network or database access. `store/collection_jobs.rs` publishes them through the existing Rust workspace transaction boundary.

A canonical UUID request key binds normalized selected URLs and immutable limits. Repeating it with identical input returns the existing job without a revision change. Another input fails. One to ten credential-free HTTPS seeds on port 443, exact selected hosts, two expansion hops, 50 charged attempts, 600 seconds and 2 MiB per response remain the upper bounds. Defaults belong to the future queue interface; this private method requires explicit bounds. Eight jobs may be queued, running or interrupted; only one can run. A job has at most eight execution generations and 256 events. Records and response Evidence metadata are limited to 4 MiB at this reader boundary, with oversized stored bodies refused before copying across SQLite. No metadata is truncated to fit.

Every record contains an event journal and a cached checkpoint. Inspection replays every event using hash-verified original bytes, reconstructing the frontier, visited URLs, robots decisions, request count, ancestry and state. It requires exact equality with the stored checkpoint. Supplied frontier caches, parent changes, extended deadlines, altered digests and unsupported record versions fail closed. This is consistency validation, not a cryptographic signature against an owner who can rewrite the database and originals.

| Boundary | Persisted behaviour |
|---|---|
| Queue | Request-key mapping and new run publish together. No request is charged and no deadline starts. |
| Start/resume | A private UUID lease identifies the execution generation. First start fixes the original deadline. Resume increments the generation and never resets counts, frontier, hop ancestry or that deadline. An expired resume commits quota exhaustion and returns no lease. |
| Advance/reserve | Apply local robots and deduplication decisions, then atomically allocate the request sequence and charge its budget before returning the private request ticket. There can be only one unresolved reservation. No request may be dispatched until that transaction succeeds. |
| Complete | Validate sanitized response facts, retain complete bytes, then atomically write Evidence/acquisition, any static text derivative, the settled request and its resulting frontier/checkpoint. A failed transaction cannot publish a derivative or frontier separately. |
| Replay | Identical ticket, canonical response facts, bytes and completion timestamp return the current record without another revision, history row or acquisition. Conflicting replay fails. A caller retries publication with the same retained result, never by rerunning a request. |
| Recover | Under exclusive ownership, a running run becomes interrupted; if cancellation was already requested it becomes terminal cancelled instead of being stranded. Its unresolved reservation remains charged and becomes `interrupted_unknown`, with a recovery time but no invented response/end time/hash. Ordinary workspace opening does not recover these records. |
| Continue | Explicit resume visits only remaining frontier entries. An uncertain page request is not retried. An uncertain robots request blocks that host; resume cannot treat it as permission or silently reacquire it. A future explicit retry policy would need a new charged request. |
| Cancel | Queued or already recovered interrupted work can be cancelled without new requests. Running cancellation remains requested until the caller establishes quiescence. Complete bytes received in a cancellation race are retained, but no new text promotion or link expansion occurs. Evidence JSON is bounded after acquisition/promotion and before publication, so escaped text cannot commit a checkpoint whose reader would later refuse it. |

The private stop-acknowledgement operation is a state seam for synthetic tests. There is no production caller proving that a network operation has stopped. It must not be exposed as a frontend assertion. An acknowledged stop may retain an unknown request outcome: stopping locally cannot establish what a remote server received.

Complete empty bodies, robots rules, redirects, errors and unsupported content are ordinary content-addressed Evidence. Only complete HTTP 200 UTF-8 HTML/plain text may gain static text, using the existing collector's extraction helper. Raw markup is never executed. Existing acquired text and source-origin groups survive later error responses with identical bytes. Distinct requests retain distinct acquisition contexts; replay cannot append another. No observations are created, accepted or rewritten. Static text promotion preserves the existing finding-invalidation behaviour; existing receipt records and previous exports are untouched.

Shared helpers come from the existing collector: seed/URL validation, request budget reservation, media-type normalization, robots matching, conservative crawl-delay handling and static text/link extraction. The legacy broker's behaviour is unchanged. New frontier state retains the existing 500-entry/visited bounds. If newly extracted links exceed available frontier capacity, this new policy records quota exhaustion rather than implying exhaustive traversal. Redirect depth is at most five; robots and redirects consume the same request budget. A completed final response at the exact request-count limit can succeed when no frontier remains. HTTP 429 records quota exhaustion without retries.

Terminal states distinguish successful, successful-no-results, partial, blocked, quota-exhausted, cancelled and failed. Partial requires retained searchable pages plus a blocked, failed or unknown acquisition; charged-request facts and retained-page counts remain visible independently of the terminal state. Quota/cancellation can therefore retain useful earlier evidence without becoming success. This foundation does not generate a receipt v1 for these jobs: that schema cannot express unresolved reservations or resumed execution.

## Time and ownership limits

The first execution fixes a UTC millisecond deadline; downtime counts. Resume cannot extend it. Event times must be nonnegative, monotonic relative to preceding events and no more than five seconds ahead of the local clock. Backwards recovery time fails. The synthetic seam supplies times explicitly, permitting deterministic crash tests. It does not measure real elapsed execution or claim that wall time is a monotonic clock. Live integration must enforce the remaining deadline with a monotonic clock inside each process segment, retain those observations separately, and fail safely on clock discontinuity. No historical continuous monotonic duration is invented across restart.

A private ownership guard acquires the existing workspace coordinator lock and explicitly unlocks it on drop. It cannot be borrowed for another workspace. This prevents concurrent synthetic owners and ordinary open cannot invalidate a running run. The eventual coordinator must own this lifecycle; this guard is not permission to launch a second independently operated scheduler. Generation and lease checks prevent stale reserve/complete/cancel actions. Response publication also uses the loaded workspace revision, so another canonical writer causes a conflict rather than overwriting its evidence changes.

## Storage compatibility and recovery evidence

No storage migration is needed for this increment. Storage schema **4** is unchanged. New `collection_run` and `collection_run_key` kinds use existing generic records/history tables. Legacy interruption recovery scans only `kind='job'`; it does not reinterpret these new records. Existing schema-4 backup copies the entire SQLite snapshot and each ordinary Evidence original. A completed response is referenced by Evidence in the same transaction as its durable completion, so the old backup code does not need to understand the new job format to retain those bytes.

A transaction failure after writing an original can leave an unreferenced file. Existing snapshot backup deliberately excludes that orphan. The reservation remains charged; publication can retry the same bytes, or recovery records uncertainty. No path claims that filesystem retention and SQLite commit form one atomic operation. Corrupt published originals are refused, never silently replaced with a later response.

The compatibility test executes a separately built pre-foundation development binary, opens a running new job, invokes its unchanged backup command, and verifies that revision/checkpoint remain unchanged. Current restore then verifies the exact run and every referenced original. The tested binary's SHA-256 is `2e2d59a493869726a45b50ff68440a287f0d7c4eaf6f8cf91e265ebf9104be59`, recorded by the preceding desktop-summary handoff (core base `ad74c03`, facet dependency `903ac02`; the foundation base is `f2b1e9a`). The previous schema-4 binary cannot inspect or execute these new jobs, and is not claimed to understand their integrity rules. Readers that reject storage schema 4 still fail closed through the existing newer-schema check. No claim is made about arbitrary historical binaries.

The backup/restore implementation itself is byte-unchanged in this increment. Its shared original verifier now delegates to `store/originals.rs`, which reads at most expected bytes plus one, subject to the 16 MiB import ceiling (zero remains valid for complete HTTP bodies). It validates canonical digest identity, a no-follow regular-file handle, exact bytes/hash and final handle/path metadata. Unix rejects hard links and checks device/inode/change time; Windows opens without write/delete sharing and checks handle/path metadata. New checkpoint replay consumes that verified buffer without reopening the file. Older callers that perform another read/copy after verification remain separate follow-up work; this does not claim to remove every existing filesystem race. A hostile same-user process racing ancestor directories is still outside the application-owned-directory assumption. Tests also retain real legacy collection receipts and their history verbatim while adding new checkpoints, preserve existing observations, and verify that same-body acquisitions share an original without erasing text or origin grouping. A new integrity reader refuses missing/altered evidence, changed key/digest bindings and malformed event/checkpoint data.

## Verification and remaining work

Synthetic tests cover queue-key conflicts and limits, exclusive ownership, charge-before-completion, crash before/after reservation, interrupted robots, stale generations/leases, redirect and link ancestry, exact last-request success, fixed deadlines/backwards time, HTTP outcome distinctions, cancellation races, atomic publication rollback, conflicting/identical replay, malicious caches and source retargeting, record size/unknown fields, prior receipt preservation, and backup/restore including an orphan file. Existing collector/receipt regressions exercise the shared helper refactor. The older-reader integration case is ordinarily ignored because it requires a separate pinned binary; it was explicitly executed for this handoff. Final ordinary verification passes **288 tests** (221 library and 67 integration), with 22 specialized tests ignored by default, including that separately executed older-reader case. Strict debug and release Clippy results and log digests are retained in the accompanying verification record. The Mac development host exercised Unix growth, replacement, links and corruption. The Windows-only sharing regression has not run locally; hosted Windows source tests and Windows 11 installed-package acceptance remain separate requirements.

Initial incomplete-source/type-check attempts failed during implementation, and the first broad run after the shared-reader change found one existing source-inspection error-message assertion. Restoring the established `checksum mismatch` wording fixed that compatibility regression without changing the assertion. Peer review identified and repaired cancel-before-crash stranding, the second unbounded original read and oversized escaped Evidence publication. Failures and final observations are retained in the verification record; they are not rewritten as passes.

The next required slice is a genuinely cancellable Rust-owned transport and coordinator integration with synthetic DNS/connect/TLS/body interruption tests. It must preserve destination validation, DNS pinning, TLS verification, exact selected-host scope, explicit request disclosure and joined shutdown. Only afterward should commands, versioned public progress/receipt schemas, designed UI controls and harmless live observations be added. No source-access approval, relevance label, broad-search benchmark pass or complete-release result is established here.
