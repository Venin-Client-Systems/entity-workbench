# Prepared public v4 cancellation

This EW-22 / #25 increment changes only the existing public `CancelCollection` implementation. Normal native collection remains disabled. Command and DTO schemas, historical policy and record bytes, UI, catalogue/resume routing and transport behavior are unchanged. Verification uses synthetic records and the existing local TLS fixture; it performs no native/public-network campaign.

Previously the public handler held workspace → collection-lane locks while inspecting the run, loading it again to append Cancel, and inspecting it again for the response. The current token was signalled after the second replay, but the acknowledgement's third replay still held both locks. The new path captures once, replays once outside both locks, then consumes an exactly revalidated private proof. The acknowledgement is projected from that validated state rather than loaded and replayed again.

## Capture, preparation and publication

The new private cancellation module reuses the existing shared capture and revalidation. Capture binds the workspace and ownership lifetime, raw canonical run and request-key identity, attached v4 protocol/mode, requested generation, and original/acquisition metadata. The complete run includes its lease, input, request sequence/history and first deadline. The existing limits apply: 4 MiB run/per-Evidence bodies, 16 MiB aggregate source metadata, at most 50 distinct original bodies, and one verified bounded body read at a time. Capture is not permission to start transport.

The capture and prepared proof are non-cloneable and non-deserializable. Exactly one historical replay runs outside workspace/lane locks and the SQLite transaction. Final revalidation requires executable ownership, not merely still-held quarantined publication ownership. It rechecks the captured run and source metadata identities and original hashes. Only the exact run or a single canonical Cancel after its exact prefix is accepted. The suffix is applied with the existing historical ordering rule and must reproduce the whole current record. Recovery, another reservation/receipt, changed generation/lease/mode or altered source fails without signalling a token or appending a new event. An unrelated revision may advance before final revalidation; later publication uses its pinned revision and never adopts another writer's revision.

The final one-use cancellation candidate contains the validated post-Cancel state and exact projected revision. Its inspection uses the same pure canonical projection and runtime/control decoration as ordinary inspection. The response bound and JSON conversion finish before the canonical write. An oversized acknowledgement, source failure, unavailable ownership, timestamp error or failed SQL publication cannot cancel a token or return success. The candidate is consumed; there is no automatic conflict retry.

A new Cancel commits exactly one canonical event/revision. An already-recorded Cancel is acknowledged without another write, including the permitted concurrent single-Cancel suffix. Even the idempotent candidate refuses an intervening canonical revision before acknowledgement. After a successful commit the handler reads the **currently locked** matching job/generation token and signals it, drops workspace/lane locks, wakes existing workers and returns the preflighted response. It never reuses a token captured before preparation, joins workers, or acquires the document active registry while holding these locks.

## State and clock meaning

A Running acknowledgement records `cancellation_requested = true`; it does not claim that transport has stopped or that the outcome is terminal. The existing receipt/settlement path retains completed bytes and decides the final outcome after transport returns. Queued and Interrupted records preserve their existing terminal Cancelled transition. Pending-publication retry remains a separate publication-only control and retains its existing rules; this change does not make public Cancel executable under quarantine.

Fresh public Cancel uses the existing strict wall-time and ordered-event validation. There is no clamping and no extension of the settlement-only anchored shutdown exception. An already-canonical Cancel remains interpretable after wall-clock rollback using the reviewed historical replay/suffix path, with its exact timestamp preserved.

Releasing both locks during preparation creates an observable conflict window: a legitimate settlement or recovery may advance the run before final revalidation. That returns an explicit error and does not retry or cancel a newer execution. The existing UI already presents control outcomes as unconfirmed on error and requires refresh before another action. No UI or wire change is needed. Runtime availability and controls describe the sampled state, not a promise that a later shutdown or quarantine cannot occur.

## Verification and remaining limits

Seven new store regression groups cover one replay; exact event/response parity with the existing cancellation implementation; unchanged request charges, deadline, evidence and reopened records; queued/interrupted terminal states; canonical Cancel suffix idempotence; recovery/reservation/source/mode/owner drift; fresh-clock refusal and historical future Cancel after rollback; response preflight, SQL rollback and revision conflicts; and refusal of historical or different-mode protocol fallback. Ready candidates also recheck executable ownership at commit.

Four new coordinator groups use actual canonical records and the existing synthetic local TLS fixture. A controlled pause **after capture and before replay** permits another thread to acquire both locks and perform an unrelated canonical write. Source placement establishes the subsequent outside-lock replay; per-thread instrumentation counts one replay. An executor independently reads the committed database after receiving its token signal. Other cases prove oversized-response preflight and failed publication do not signal, exact concurrent Cancel does not add a second event, and recovery/quarantine/stopping during preparation refuses without cancelling the current token. The oversized response is an explicitly injected guard fixture, not a claim that ordinary bounded records naturally produce that size.

These checks are not a full-duration mutex measurement or latency/RSS benchmark. Preparation still precedes token signalling and is not cooperatively preempted. Capture, final source metadata checks, up to 50 historical original rehashes, response projection/serialization and canonical I/O still occur under the workspace/lane locks. Ordinary inspection, catalogue, resume/start, recovery and direct store operations retain their existing replay behavior. No hard cancellation deadline, general responsiveness, native-platform evidence or production-activation acceptance is claimed.
