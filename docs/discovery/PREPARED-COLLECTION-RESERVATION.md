# Prepared v4 request reservation

This EW-22 / #25 increment removes duplicate historical replay from the automatic v4 next-request path. Normal native collection remains disabled. It introduces no command, schema, policy/version change, dependency, persisted cache or native/public-network campaign.

Previously, `CollectionDriver::next_with` held the workspace mutex while taking a full execution snapshot and then loading/replaying the same run again for Advance. A cancelled token added a third replay for Cancel. The new v4 path captures canonical inputs once, replays once outside the workspace mutex and SQLite transaction, then consumes a revalidated proof to publish the same canonical transition.

## Shared proof and reservation

The existing settlement capture, historical replay and final revalidation live in one private `collection_replay` module. Settlement and reservation reuse that implementation. Capture still binds the workspace, ownership lifetime, exact raw run, request-key mapping, source metadata and original references. It preserves the 4 MiB run/per-Evidence limits, 16 MiB aggregate source metadata preflight and at most 50 distinct historical originals. Original bytes are read through the existing bounded verifier, one historical body at a time. A capture failure is an operational refusal, never a partial interpretation or a new canonical quota classification.

The capture and prepared state are private, non-cloneable and non-deserializable. Reservation captures the exact execution ticket, driver input and first-start deadline. The driver also retains its attached protocol; an attached v4 driver rejects a later record changed to v2/v3 or another acquisition mode instead of falling through to legacy execution. Genuinely attached historical transport drivers keep their prior path and policy meaning.

After outside-lock replay, publication checks **executable ownership** and canonical quarantine. Still-held quarantined ownership remains usable for an already-owned receipt's settlement only; it cannot reserve another request. Shared revalidation demands unchanged run/source identities and verifies originals again. The only acceptable run suffix is one canonical Cancel after the exact captured prefix, reapplied with historical ordering and checked against the entire current record. Recovery, a changed lease/generation, another reservation, altered metadata/originals or a forged checkpoint fails without a new charge or fetch. Unrelated revision advancement is acceptable only when all captured identities remain exact; publication uses the newly pinned revision.

## Exact writes, cancellation and clocks

The driver samples wall time after preparation. Its process-segment monotonic deadline and canonical first-start deadline remain unchanged. Fresh Cancel and Advance use the existing strict current-time and ordered-time validation. This does not extend the settlement-only anchored-stop exception to arbitrary new events: a future-dated historical checkpoint can still be replayed, but cannot authorize a backwards or future new reservation timestamp. A refused pre-reservation clock transition does not claim transport cancellation or charge a request.

If a cancelled token requires a new Cancel, that event is committed as its own canonical write. Advance is then committed separately, as before. The second write expects exactly the first write's revision plus one; it does not adopt another writer's intervening revision. Failure of Advance leaves the successfully committed Cancel intact, with no request ticket returned. An already-recorded cancellation does not get another Cancel event. Advance finishes it without an additional request charge.

The fetch closure is invoked only after a returned reservation commits. Capture/replay/revalidation/write errors do not retry implicitly and cannot invoke transport. If cancellation occurs after reservation, the existing transport token and truthful receipt path remain responsible for the charged request; no charge is refunded. Existing pending settlement ownership, explicit publication retry, raw-clock retention, unknown-termination quarantine and joined shutdown rules are unchanged.

## Verification and limits

Seven new real-store groups cover exact serialized parity with the existing Cancel/Advance implementation, revision counts, a single replay, canonical Cancel suffixes, recovery/source/owner drift, unrelated revisions, input/deadline mismatch, same-length original tampering, separate-write rollback and intervening revision refusal, fresh timestamp rejection and expiration of the unchanged first deadline. Existing prepared-settlement clock-rollback and receipt-retention tests also run after the shared-code extraction.

Four driver groups use the existing synthetic local TLS fixture. They check a committed charge before transport, one replay per next-request attempt, cancellation during a bounded test pause, drift/publication failures with no fetch or retry, and attached protocol/mode refusal with a valid historical control. The test hook pauses **after capture and before replay**. The mutex check demonstrates access and a canonical write during that pause; source inspection establishes that the subsequent replay is outside the mutex, and per-test-thread instrumentation counts replay calls. These are not full-duration lock measurements or latency/RSS benchmarks.

Historical schema bytes, original/acquisition contents, event order, existing policy identities and the first deadline are preserved. No public catalogue/control API or acknowledgement semantics changes. Public inspect/page/cancel/resume, initial attach/start, startup recovery and direct store Advance still use their existing replay paths, potentially under the workspace mutex. Capture metadata, final original rehashes and canonical I/O remain mutex-held. Parser work is not cooperatively preempted, and this slice gives no hard cancellation deadline or general responsiveness guarantee.
