# Prepared v4 collection settlement

This EW-22 / #25 increment moves coordinator v4 settlement's historical replay and new response interpretation outside the workspace mutex and SQLite read transaction. It preserves the existing v4 HTML policy and canonical receipt meaning. Normal native collection remains disabled. It adds no command, schema, dependency, persisted derived cache, public-network invocation or native acceptance claim.

## Capture, interpretation and publication

The existing coordinator owns the same `PendingSettlement`, including its exact complete response bytes, throughout preparation and publication. Under the workspace mutex, capture pins one SQLite read snapshot and reads the current revision, exact run body and request-key mapping. It validates the current protocol/input, ownership lifetime, charged ticket and transport receipt. It captures referenced Evidence metadata with content-addressed key/body/digest and byte-count checks. No database handle escapes capture.

The mutex and transaction are then released. A private, non-cloneable, non-deserializable capture replays the original journal using the existing state machine, acquisition checks and bounded original reader. It reads one historical original at a time. It applies the pending receipt through the existing interpretation rules and produces a consumed preparation handle containing the verified prefix and computed resulting state. The handle is not a serialized worker result or a caller-authored checkpoint.

Publication reacquires the workspace mutex and a fresh read snapshot. It requires the exact workspace root, still-held publication ownership lifetime, ticket and transport receipt, including a freshly computed body digest. Same-length body substitution fails both preparation and publication. Every captured source metadata body must retain its exact hash, and every referenced original is read and hash-verified again. An unrelated workspace revision may have advanced; final canonical publication uses the newly read revision through the existing revision-checked atomic writer.

The run must retain its exact captured body, with one narrowly defined exception: it may contain exactly one appended canonical `Cancel`, after the exact captured event prefix. The existing cancellation transition is applied to the verified prefix, and the **entire resulting run** must equal the current canonical record. Different checkpoints, another event, recovery, a changed lease/generation, or another source interpretation fails preparation/publication and requires an explicit fresh attempt. No arbitrary new run state is accepted.

The stored Cancel suffix uses historical timestamp ordering, so a wall-clock rollback after its publication cannot invalidate it. Newly requested ordinary cancellation still uses the existing current-time validator. For coordinator stop intent when the sampled time is earlier than the validated journal checkpoint, the existing anchored-cancellation helper records that exact checkpoint anchor. The receipt's raw observed wall time is never clamped. Unknown termination and clock failure retain their existing precedence over cancellation.

## Cancellation, errors and recovery

A cancellation command can acquire the workspace mutex and commit while new-response interpretation is paused outside it. Interpretation itself is **not cooperatively preempted** by the cancellation token; its existing bounded parser work may finish. Publication rechecks canonical cancellation and applies the same receipt with cancellation already set, which suppresses new text/link promotion while retaining the truthful complete original and acquisition. No follow-up fetch is taken from a cancelled interpretation.

Joined shutdown waits for the collection executor, including preparation, before releasing ownership. Preparation failure, source drift, stale state, or an atomic publication failure leaves the existing `PendingSettlement` body owned by the lane. The existing bounded explicit settlement retry recaptures and interprets that same receipt; it never refetches, refunds a request charge or starts an independent retry loop. Files retained before a failed canonical write may remain unreferenced under the existing original lifecycle.

An already-settled exact receipt is fully replayed and its acquisitions/originals verified, then returns the same run without a revision increment, new acquisition or canonical write. A crash before publication has no durable preparation cache: reopening and ordinary recovery preserve the original request charge and mark the unresolved reservation as interrupted/unknown. The first-start deadline is unchanged. A handle from a released owner cannot publish under a replacement owner, even if the canonical request remains the same.

V1–v3 settlement follows its existing path. V4 retains its existing interpretation meaning; historical in-limit replay and explicit pathological-history refusal are unchanged. No record is migrated or re-encoded merely by reading. All 100 tracked schema-directory files (98 JSON schema files plus README and runtime inventory) remain byte-identical to the base.

## Resource bounds and remaining mutex work

Capture preflights the serialized run at 4 MiB, up to 50 distinct historical response references, each Evidence record at 4 MiB and their aggregate serialized metadata at 16 MiB **before copying any of those metadata bodies across SQLite**. A capture refusal is an operational preparation error with the pending receipt retained, not a new canonical quota classification or partial result. An otherwise individually readable large acquisition history can therefore require operator recovery rather than automatic settlement. The existing pending body and each historical body are bounded at 2 MiB. Internal Rust allocations, state clones and parser work are not described as a hard RSS bound.

This is a focused settlement seam. General inspection, cancellation, start, advance and their existing read paths still replay historical HTML while holding the workspace mutex. Capture reads/decodes bounded canonical metadata under it. Commit rehashes up to 50 historical originals and writes/syncs the new original under it; canonical serialization and publication also remain there. The slice does not establish general UI responsiveness, bounded filesystem latency, total CPU instructions, a hard elapsed-time limit or a cancellation deadline. Parser-internal calls retain the limitations documented in [bounded HTML interpretation](BOUNDED-HTML-INTERPRETATION.md).

## Synthetic verification

Real canonical-store tests cover unrelated revision advancement, exact receipt idempotence, source metadata/original tampering, replaced ownership, same-length response substitution, forged cancellation checkpoints, non-cancellation run drift, preflight limits, publication rollback, explicit retry, backup/restore and crash/reopen with an irrevocable unknown charge.

Two deterministic rollback regressions failed before the repair with `Invalid or future collection timestamp`: stop during prepared publication and an already-published canonical Cancel suffix. Their repaired assertions retain exact raw receipt/body bytes, clock-failure precedence, anchor identity, idempotence and reopened state. No OS clock is changed.

Two ordinary coordinator tests use the existing local TLS fixture and actual queue/reserve/transport/settlement path. An instance-scoped test-only pause before interpretation proves canonical cancellation can commit while the workspace is unlocked, and separately proves shutdown cannot release ownership before preparation joins. Both retain complete response bytes without promoting text and stop after exactly robots plus the selected seed. These are synthetic local-fixture checks, not native DNS or public-network observations. Prior fixed native proof source and receipts are unchanged, and every activation/release gate remains unchanged.
