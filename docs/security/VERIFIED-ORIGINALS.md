# Verified original bytes and bounded copies

The canonical original reader introduced with the durable collection foundation now supplies the bytes consumed by document processing, workspace backup/restore and collection-bundle export. These paths no longer verify an original and then reopen its source path to read or copy it. This closes that specific follow-up recorded in [the foundation contract](../discovery/DURABLE-JOBS.md); its earlier verification record remains historical evidence.

`store/originals.rs::read_original` requires the canonical Evidence ID and SHA-256 to agree, enforces the 16 MiB import-policy ceiling (zero is valid for complete HTTP responses), and reads through a no-follow regular-file handle with an expected-length-plus-one cap. It checks the exact length and digest and compares final handle/path metadata. Unix rejects hard links and uses device/inode/change-time checks. Windows opens without write/delete sharing and checks handle/path metadata. The later shared file-identity follow-up also requires a single hard link and the full 128-bit handle identity before and after reading, including a newly opened final named handle. The same narrow Win32 adapter is used by immutable derivatives and native export verification; no dependency is added by this follow-up. The prior foundation record contains the Unix growth/replacement/link regression results; native Windows sharing, hard-link and handle-identity behaviour still require their platform run.

The consumer changes are intentionally narrow:

| Consumer | Behaviour |
|---|---|
| Processing preparation and publication validation | `verify_processing_input` returns the shared reader's verified buffer directly. The lookup Evidence ID must match the job input ID, digest and length; a different valid original cannot substitute for that key. A missing, altered or linked source prevents a prepared worker input and retains the existing blocked/input-unavailable outcome. |
| Backup and restore original copies | Each source is read once into its bounded verified buffer. Copying retains existing source/destination exclusion rules, private directories, collision refusal, snapshot reference selection and database publication ordering. An incomplete copy does not create a usable restored database or a completed backup manifest. Existing partial-directory lifecycle remains unchanged. |
| Collection export originals | Each deduplicated original uses the same buffer-copy helper. UUID staging, immutable manifest bindings, database publication and cleanup of the current attempt are unchanged. A failed final transaction removes that attempt's staging/published directory while preserving earlier exports. |

The private `write_verified_copy` helper accepts only an internal destination and an already verified buffer. It independently checks the bounded identity, size and digest before creating a file, refuses existing names through `create_new`, writes the exact bytes, applies Unix 0600 then 0400 permissions through the file handle and syncs before closing. It then verifies the destination through the same bounded no-follow reader. It supports both canonical backup filenames and collection export's `.bin` names. It is not a public arbitrary-file API. Existing Windows file-mode behaviour is retained; the helper does not introduce an application-level encryption claim or change directory ACL policy.

A deterministic test obtains a verified original buffer, replaces the source file, then copies the retained buffer successfully: the destination contains the exact verified original while the changed source fails fresh verification. This proves that copying does not reopen the replaced source. Separate tests cover mismatched/oversized buffers, existing and linked destinations, exact bytes and Unix modes, complete empty originals, wrong-key/valid-body processing substitution, source corruption/links, backup destination exclusions, corrupt restore input and collection-export transaction rollback. Existing recovery, receipt, processing and snapshot tests remain in the full suite.

Source inventory found no remaining production canonical-original verify-then-reopen consumer in the Rust store. Remaining `verify_original` callers check provenance before using canonical metadata or text; they do not reread raw originals. Worker assignment files, engine caches, derivative files and the backup manifest are different data classes and are not claimed to be covered by this audit. Separate metadata lookup-key validation work is also outside this byte-consumption patch.

All originals, database directories and export staging remain application-managed. This is bounded file validation and consistent snapshot handling, not cryptographic immutability against a hostile owner process racing the filesystem. No public command, schema, dependency, native download/export transport, or UI changes are included. The verification record records the actual host and results; it does not stand for Windows 11 installation, signing/notarization, offline packaging or any complete-release gate.
