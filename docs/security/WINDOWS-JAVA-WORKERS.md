# Windows Java engine recipes — development candidate

This adds **engine-only development recipes**, not Windows application support. The core parser, Lucene adapter, OCR and desktop routes remain unchanged and continue to block unverified Windows workers. The preceding [AppContainer foundation](WINDOWS-WORKERS.md) has a retained development-probe pass; that evidence does not establish these new recipes. Their native results remain **unverified until the extended workflow actually runs**.

The separate Rust crate exposes three closed constructors: parse one byte buffer; index a bounded document manifest at a specified revision; and search a previously accepted in-memory index snapshot. Callers cannot supply relative input names, Java class names, JVM options or system properties through these constructors. The existing low-level launcher remains a trusted coordinator interface, not a user extension mechanism.

## Assigned data and runtime separation

| Process | Read-only inputs and executable assets | Writable assignment | Accepted output |
| --- | --- | --- | --- |
| Parser | Copied Java; parser-only worker classes and non-Lucene dependencies; one immutable document; immutable request metadata | Disposable scratch and its existing private AppContainer profile | At most 2 MiB JSON, bound to generated job ID, input size and SHA-256 |
| Index builder | Copied Java; search-only worker classes and Lucene/Jackson dependencies; one immutable manifest; immutable request metadata | A fresh index under disposable scratch, plus the existing private profile | Strict matching document-count/revision acknowledgement and bounded validated index files |
| Search | Copied Java; search-only worker classes and Lucene/Jackson dependencies; immutable query/request; a copied read-only index snapshot | Disposable scratch and its existing private profile | At most 1 MiB JSON, matching snapshot revision and known unique source IDs/names |

Every operation launches separately. The parser receives no search runtime, index grant or canonical workspace. Search receives no parser runtime or private original-document grant. The index build directory is disposable; no worker receives an existing writable cache or a canonical database path. Rust owns the in-memory handoff and verifies it again before staging a separate read-only search copy.

The production ACL masks, zero capability list, suspended token verification, one-process Job Object, strict handles, detached launch, no inherited handles, sampled resource limits and explicit stop/cleanup policy are unchanged. Native input metadata uses the same read-only package grant as the existing assigned input. A search snapshot receives that read-only grant for its directory and files. The builder's new index directory inherits the existing scratch grant. No additional network permission, process allowance or unconfined retry is added.

`FileWorker` is a small Java file-IPC bridge: it opens and bounds its assigned request, requires a fixed parse/index/search operation match, then supplies those bytes to the existing worker's stdin reader within the same process. There are no inherited pipes or helper processes. `Protocol.input` supports one coordinator-supplied absolute assigned-input property only for the exact request name `input.json`. It still runs the existing relative-name checks first. With that property absent, the macOS behavior is unchanged. Output continues to use the existing relative `result.json` contract in scratch.

## Runtime inventory and bounded handoff

[`stage_windows_engines.py`](../../scripts/stage_windows_engines.py) reads an already installed local Java 21 and the existing Maven build output. It performs no download or engine execution. It copies Java separately for parser and search, extracts only reviewed worker classes, excludes all Lucene-named dependencies from the parser and includes only Lucene/Jackson dependencies in search. Existing direct dependency pins remain Tika 3.3.2, PDFBox 3.0.8, Lucene 10.5.1 and Jackson databind 2.22.3. No dependency version changes are introduced. Rust additionally uses the workspace lockfile's existing `sha2` 0.10.9 and the existing UUID dependency's serde feature.

Each role gets a complete manifest of regular files, sizes, SHA-256 hashes and directories. A root development marker is created only after both roles stage successfully. Selected worker classes are checked against their declared ZIP size and read through a 1 MiB + 1 cap; duplicate archive entries and oversized classes reject staging. Partial staging is not a ready bundle and must be discarded before retrying with a fresh destination.

Before execution, Rust requires the exact role, required pinned library names, permitted role-specific asset locations, complete inventory equality and all file hashes. Missing and unlisted assets, case-colliding or unsafe names, links, Windows reparse points, hardlinked files and nonordinary ancestors are rejected. The copied runtime is verified again before execution. The existing native walk also rejects named streams. These manifests bind actual development bytes; they do not replace a signed release manifest or independent dependency review.

The bounded transport uses:

- At most 16 MiB assigned document or encoded index manifest, 10,000 index documents, 128-byte IDs and 1,024-byte names. Aggregate source-string lengths are checked before identity copies. A borrowed manifest is serialized directly through a 16 MiB capped writer, so JSON escaping cannot cause an unbounded intermediate value or output buffer.
- Fixed JVM heap of 256 MiB, two reported processors, serial GC, assigned scratch for temporary/home paths, a 768 MiB process commitment limit and a 30-second worker wall time. These are development limits, not throughput claims.
- At most 128 flat index files, each at most 8 MiB and together at most 24 MiB. Traversal, device names, streams, case collisions and missing commit files are rejected. The native collector retains the directory pin, rejects links/hardlinks and reads each file under a bound after process exit. Rust computes file hashes, checks the matching acknowledgement and validates the snapshot before returning it.
- A generated job UUID and input hash/size for parser results; exact revision/document count for index results; matching revision, finite scores, at most 100 hits and known unique source identities for search results. Unknown fields, duplicate struct fields and trailing JSON are rejected. These are transport checks; canonical domain validation and source-anchor acceptance still belong to the core coordinator when integration is implemented.
- Immutable input/request bytes and every assigned search snapshot file are checked again after worker exit. Results are rejected if assigned inputs changed. Existing cleanup failures continue to reject the result and retain preceding errors; cancellation is checked again after successful cleanup before returning an accepted Java output.

No snapshot is published to a workspace, no revision marker is written and no database migration occurs in this slice. A stale or malformed worker acknowledgement cannot create an accepted `IndexSnapshot`. Its fields are private; search accepts only a checked snapshot object, not a caller-selected filesystem directory.

## Native development verification

The extended [`windows-confinement.yml`](../../.github/workflows/windows-confinement.yml) keeps the existing foundation tests and complete hostile/copied-Java probe mandatory. It then builds the existing pinned Maven worker project and its Java file-path tests, stages separate local runtimes, and runs `ew-windows-java-probe` on Windows Server 2022. The Maven build may obtain pinned build dependencies; neither staging nor the launched application worker downloads assets. No OCR runtime, model or asset download is introduced.

The engine probe compiles synthetic fixtures from the repository into its binary. Its prepared cases are:

1. Actual UTF-8, searchable PDF and DOCX extraction with expected text and status; an image-only PDF remains explicitly partial; an unsafe ZIP yields the expected archive-limit failure; unsupported bytes remain unsupported.
2. A distinct Lucene process builds an index from the actual accepted extraction texts. Separate read-only search processes exercise Boolean, phrase, proximity, fuzzy, fielded and successful-no-results queries, checking exact revision and expected source identities/counts.
3. Each runtime executes the reviewed synthetic Java boundary worker. Matching unconfined controls run before and after its confined invocation. Twenty predicates cover assigned input/request reads and writes, runtime write access, the other actual runtime, a private workspace, the actual synthetic original, a real captured sibling Lucene snapshot, scratch I/O, direct loopback TCP, child-process creation, the real caller environment sentinel, classpath separation and read-only assigned-index access. Parser/Tika classes must be absent from search, and SearchWorker/Lucene classes absent from parser.
4. The parent verifies each complete predicate map and empty job directories. A failed JVM launch, process exit, missing result or cleanup failure cannot substitute for a boundary result. Successful file-handle, socket or child creation is not converted into denial by a later I/O/cleanup error. Such later errors fail the probe. The assigned-index read/write predicates apply only to search; the parser has no such grant.

The workflow initializes a failed/incomplete Java receipt before building anything. Only the completed native executable can replace it with success. It retains both role inventories, source/OS/runtime identities, the compiled probe hash, the original foundation report and the separate Java report on failure or success. Reports contain fixed test labels, booleans, counts, versions and hashes, not private paths, account identifiers, arbitrary exception text or actual investigation data. All original foundation failures and its first pass remain recorded in the linked foundation document.

## Current evidence and remaining work

Local verification passed **22 Rust tests** (including the existing portable launcher/probe tests and new recipe/reply/inventory/snapshot regressions) and **five synthetic Python staging tests**. The prepared Windows suite contains 37 Rust tests; it has not run for this candidate. Host and Windows-target strict Clippy, formatting, workflow lint and diff checks passed; cross-compilation does not run native code. The changed Java main classes compile with `javac --release 21` against the already built pinned local dependencies; the available compiler is Java 25, so this is not a Java 21 native compatibility claim. Java 21 compilation, the added JUnit tests and actual parser/Lucene AppContainer outcomes await the hosted run.

The work remains blocked from application use pending native results and review. Additional work includes the actual selected release runtime, Windows 11 downloaded-installer testing, coordinator integration and atomic workspace publication, durable recovery, cancellation/restart scenarios for real engine jobs, broader hostile documents, filesystem race stress, non-loopback/DNS/IPC coverage, signing and independent security review. This candidate does not change a release gate to passed.
