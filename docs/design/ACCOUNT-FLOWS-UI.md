# Reviewed account-flow interface

The transaction workspace now offers an explicit **Calculate reviewed flows** instrument. It displays canonical, reciprocal reviewed transfers as directed debit-to-credit lanes, separated by exact currency. Unmapped accepted activity remains visible without inventing external counterparties, ownership, matches or findings. This is the bounded EW-18 interface increment, not completion of account-flow analysis or a release gate.

## Canonical semantics and bounded presentation

The component calls `AnalyzeAccountFlows` from Command v25 with exact nullable date/account/currency filters and the current expected revision. Date bounds are inclusive. Existing whole-ledger facet readers retain exact account text, including leading zeros, and separate currencies. No frontend matching, financial arithmetic or currency conversion was added. The [account-flow engine contract](../transactions/ACCOUNT-FLOWS.md) remains authoritative.

The response's selected count includes every review state in the applied scope. Support-only rows explain the other endpoint of a verified pair outside that scope; they add neither selected activity nor selected review counts. Pending, rejected and deferred rows are separately inspectable. Accepted ledger totals include mapped transfers; accepted unmapped totals exclude verified pairs. Possible duplicate and unverified-transfer annotations overlap the review partitions and do not silently remove rows. A support-only account shows its role and sources without presenting zero as its observed financial activity.

Each lane states debit-to-credit direction in text, shows its exact currency/amount and provides its pair count. Equal-width lanes do not encode money geometrically. Repeated equal-value pairs remain distinct. Both endpoint dates, versions and scope roles appear in pair review. Relationship, account-group, pair and source lists render at most 25 entries per page with explicit shown/total counts. This is a DOM bound: the existing engine still analyses the full ledger and returns a bounded, potentially 16 MiB result with its complete source set. This increment makes no internal-memory, large-ledger latency or graph-performance claim.

Draft changes are visibly unapplied until calculation. A response must match the captured request, revision, schema and rule identifier. Unmount or a newer calculation prevents late state publication. A workspace revision change or failed calculation/refresh retains the historical result visibly stale or unverified and disables its source actions. A failed parent refresh returning `false` is treated as unconfirmed, as is a rejected promise.

Source drillthrough reuses the existing bounded `ReadTransactionSources` reader with captured IDs, versions and revision; originals are checked by Rust. The selected/support label precedes each source's review annotation. The generic word “included” is suppressed for contextual flow sources, so support is never mislabelled as selected activity. Source corruption and stale revisions remain explicit failures. The existing transaction review receives the originating result revision; no current-revision inference or substituted source text is used. The shared dialog keeps focus inside the modal and returns focus on Escape or transfers it to transaction review.

## Verification

The [validation manifest](evidence/account-flows-20260926/validation.json) binds source files, the real Rust development executables, test configuration hashes, screenshots, axe results and sanitized logs. All fixtures use synthetic data imported/reviewed/matched through canonical commands. Response substitution appears only in a negative identity test; browser tests do not replace the financial calculation.

The final focused run passed **18 tests** (11 account-flow and seven facet workflows); a compatibility run passed **28 tests** across recurring patterns, period comparison and summary-ledger workflows. The 11 account-flow cases were rerun against frozen source to refresh the visual evidence. TypeScript/production build passed, retaining the existing large-chunk warning. Three scoped axe scans returned zero violations. At a 760 × 1000 viewport, the tested panel had no horizontal overflow; modal keyboard containment, Escape restoration and source-review handoff passed. These checks are not full assistive-technology coverage or observed packaged macOS/Windows UI interaction.

The ten-row synthetic ledger covers leading-zero accounts, two currencies, eight-decimal values, repeated equal transfers, all review states and an escaped hostile description. An asymmetric January/account scope yields six selected rows, two February support rows, ten workspace rows and exactly two pairs totalling 40.00 AUD. Separate 27-pair and 27-relationship fixtures exercise page boundaries and every source/account identity. Tests also cover empty versus pending-only versus unavailable results; draft scope; real original corruption/restoration; canonical corrections; response request mismatch; held responses across remount and actual revision changes; failed refresh; source focus and exact revision handoff. Read-only flows preserve canonical state.

The first expanded run had one test-only locator failure: it sought “Transaction ledger” instead of the actual “Paged transaction ledger”. The locator was corrected without weakening a production condition. Its failed log remains retained; line excerpts in that log reflect concurrent formatting during that development run and are not treated as exact final source locations. The final source was frozen for subsequent checks. Two existing no-external-request assertions now use their configured local origin instead of a hardcoded port; facet request counts include the two new independently bounded selectors. All 100 historical schema-directory files (99 JSON schemas and their README) remain byte-identical to the base.

No Rust calculation, command, storage, schema, dependency, worker, runtime or export behaviour changed. Existing financial rules and canonical writer ownership remain intact. No new native engine or release approval is asserted.
