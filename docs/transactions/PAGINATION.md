# Revision-bound transaction pages

`PageTransactions { request, expected_revision }` is a read-only backend capability in command v12. It does not replace the historical `View` command or presentation response, and it is not yet connected to the interface. The new `transaction-page-request.v1` and `transaction-page.v1` schemas describe its public types.

The request contains `filter`, `order`, `page_size` and optional `cursor`. Filter fields are inclusive `date_from`/`date_to`, exact `account`, exact three-uppercase-letter `currency`, and optional `review` (`accepted`, `pending`, `rejected`, `deferred`). Omitted or null filter fields mean unrestricted scope. Dates and account/currency scope share the existing analysis validator; account filters additionally reject control characters. Leading account zeros are preserved. SQL-looking account text is a literal bound value, never a query fragment. No arbitrary SQL, expressions, amount sorting or transfer treatment is accepted.

`date_ascending` and `date_descending` sort on the canonical transaction date. Equal dates always use canonical record insertion sequence **ascending**, including in descending date order. Corrections keep their canonical row identity, increment the workspace revision and invalidate prior pagination. No locale-dependent comparison or floating-point amount conversion is involved.

Each response contains schema version 1, the pinned workspace revision, a query digest, scope count, review counts, selected count, exact canonical transaction rows and optional next cursor. Scope and all four review denominators apply to date/account/currency filters before the optional review selection. For example, six pending rows with an accepted-only selection returns scope=6, pending=6, selected=0 and no rows; a scope with no transactions returns all counts zero. Counts are counts of canonical ledger records, not assertions that every scoped original was reverified.

Amount, balance, currency, IDs, versions, duplicate candidates, transfer links and original source anchors are returned unchanged. The reader performs no money aggregation or analytical reclassification. It validates returned decimals and dates with existing Rust rules. Each distinct original referenced by returned rows is verified once per page; it does not rehash the entire selected ledger.

The page size is 1–200 rows. A second limit allows at most 2 MiB of retained transaction JSON bodies in a page. Candidate selection reads sequence, key and byte lengths before fetching a body. Reaching the byte limit returns a shorter page with a cursor pointing after the last **returned** row, so the first unreturned row remains eligible. An individual row exceeding the limit fails explicitly when reached; it is never silently dropped. The byte limit describes retained row bodies, not an exact IPC envelope or a process-wide memory ceiling. SQLite still evaluates JSON filters and sorts; no new persistent index, end-to-end performance target or workspace-wide paging claim is made here.

The continuation cursor is bounded to 2048 bytes, has a strict versioned encoding and binds the canonical filter, order, page size and expected revision. The cursor itself is excluded from that digest. Consumption also checks that its last date/sequence still identifies a row in the selected scope. A cursor is a consistency mechanism for one selected workspace, not an authenticated or tamper-proof authorization token. Applications should retain it opaquely and restart after a filter/order/page-size or workspace revision change.

Expected revision, review counts, cursor position and rows are read from one SQLite snapshot. Canonical changes on another connection cannot mix later rows into an earlier page. A stale expected revision returns a conflict; a stale or cross-query cursor is rejected. Reading a page creates no canonical event, decision, classification or revision.

Tests cover both date orders with ties and multiple page sizes, exact original rows and decimal strings, account/currency/date combinations, all review denominators, pending-only versus empty scope, corrections and stale/cross-query cursors, byte-limited boundaries, oversized rows, hostile parameters, unknown fields, source corruption, and an actual second canonical writer committing while the read snapshot remains open. Historical full/presentation responses remain intact. UI adoption and scale measurements remain separate work.
