# Transaction patterns v1

This is a read-only, revision-bound calculation for recurring debit candidates, cash/refund markers and original-description totals. It is a bounded part of EW-18; it does not complete statement reconciliation, period comparison, account-flow graphs, reviewed merchant identity or performance acceptance.

`analyze_transactions { request, expected_revision }` returns `transaction-analysis.v1` through command v6. Rust owns validation and every exact decimal calculation. The operation reads a consistent SQLite transaction, refuses a revision mismatch, checks retained original hashes for scoped rows and their recorded transfer counterparts, and publishes no canonical records. A correction makes the prior revision stale; earlier report exports remain unchanged. Old command schemas are preserved.

The request filters inclusive transaction dates, exact account and currency. Posting dates are not used. Amounts are decimal strings; credits and debit magnitudes are nonnegative, and net is credits minus debits. Each currency is separate, including zero totals where the scope contains only unaccepted rows. An empty scope differs from a scope with pending rows. Every aggregate carries the contributing transaction IDs; rows carry their canonical version.

The currency partition is complete and mutually exclusive: included accepted rows, pending, rejected, deferred, and explicitly excluded reviewed-transfer rows. Cash/refund hints and cadence candidates are subsets of included rows; their amounts must not be added again to the ledger total. Duplicate candidates and repeated purchases are retained.

Transfer inclusion is the default. Optional exclusion requires both sides to be accepted, reciprocal links, distinct accounts, the same currency, nonzero values and equal opposite amounts. The counterpart can be outside the selected filter. A dangling, unreviewed or inconsistent link stays counted in its review-state partition and is flagged. Exclusion never silently repairs a pair.

“Merchant” groups use original descriptions with whitespace collapsed and ASCII letters uppercased. Digits, punctuation and non-ASCII case remain significant. Grouping does not confirm the merchant, branch or transaction channel. Rows from different accounts share a description group only within one currency; account names remain visible.

Cash markers require a negative amount and a whole `ATM` token or adjacent `CASH WITHDRAWAL` tokens. Refund/reversal markers require a positive amount and a whole `REFUND` or `REVERSAL` token. These can misclassify descriptions and miss other languages or wording. A refund is not paired to a purchase or assigned a merchant by this rule. Inspect the preserved source and review the source transaction; this feature creates no accepted classification.

Recurring candidates require the entire included debit group for one account, currency and normalized description to fit a schedule. Default: at least three occurrences, at most two days from each expected date, and exactly equal amounts. Minimum occurrences accepts 3–12, date tolerance 0–3, and the amount tolerance is the nonnegative absolute maximum-minus-minimum debit spread in that currency’s units. It is not a percentage or currency conversion.

Schedules are anchored at the first observed date: every seven days, fourteen days, or calendar month. Calendar months retain the first day-of-month where possible and otherwise clamp to the target month’s last day. Deviations are actual minus expected days. The first fully qualifying schedule is returned. Same-day rows suppress the entire candidate, without deleting either purchase. Missing periods, changing descriptions, mixed activity, extra purchases and scope cutoffs can suppress candidates. No subsequence search or subscription claim is made. All eligible debit IDs and unmatched IDs remain inspectable.

The operation refuses workspaces above 100,000 transaction rows or 32 MiB of original descriptions, rather than returning truncated totals. Arithmetic overflow fails the complete calculation. These bounds are safeguards, not a benchmark or a pagination implementation. The UI renders lists in pages of 25; the analytical result itself is currently returned in full. EW-17 must establish the large-workspace execution and memory budget.

`fixtures/transactions/patterns.csv` is entirely synthetic. Its README gives independently specified expected totals. Rust tests cover the complete denominator, transfer peers outside scope, corrupted originals, same-day repeats, calendar-month ends, amount spread, drift, missing periods, empty/invalid inputs, overflow, and canonical correction freshness. Real-core browser tests exercise the command bridge; they do not mock calculation output.

Shared money validation now uses an exact decimal parser. Addition and subtraction align the original decimal mantissas into signed 128-bit integers (the supported 96-bit mantissa and eight-decimal-place input bound make this alignment representable). Only trailing zeros may be removed when returning a decimal. An unrepresentable exact result returns an error; small amounts are never silently rounded away beside large amounts. The same helpers cover existing reviewed totals and balance reconciliation. Canonical dates require exactly four ASCII year digits, two month digits, two day digits and the two hyphens, followed by calendar validation. Existing malformed stored values fail validation rather than being silently repaired.
