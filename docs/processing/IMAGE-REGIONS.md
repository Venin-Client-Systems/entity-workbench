# Retained image OCR word regions

This opt-in development path queues `QueueImageOcrRegions { evidence_id, request_key }`. It uses the existing two-slot durable coordinator, cancellation, three allocated attempts and recovery suspension rules. Existing `QueueImageOcr` still produces text-only summaries and discards its raster. The designed review interface queues this operation and displays verified retained rasters and words. It does not create an accepted observation or reviewed source anchor.

The original PNG/JPEG is decoded in the disposable confined Java image worker. The resulting canonical P5 grayscale raster is recognized by the separate app-local English Tesseract word-region worker. Rust validates the original checksum/length, decoder result and raster, then reparses the exact TSV and checks the typed recognition result. The decoder and recognition must identify different worker jobs. Unsupported, malformed and quota-rejected images retain a typed decoder result without inventing recognition or raster files. A rendered raster with no recognized words retains the raster, page-only TSV and original whitespace text, with `no_text_recognized` status.

Recognition and boxes remain unreviewed. The raw engine score is separate from analyst confidence and is not a calibrated probability. Coordinates refer to encoded image pixels converted to grayscale; EXIF orientation is not applied. TSV page 1 is this raster, not a document page. This path supplies no PDF mapping and creates no word-level source anchors. See [image decoder boundaries](../security/IMAGE-WORKERS.md) and [word-region engine limits](../security/OCR-WORD-REGIONS.md).

## Canonical records and files

Command v10 adds the queue command and `InspectImageRegionExtraction { extraction_id }`. Processing-job v4 adds only the `image_ocr_regions` operation and additive failure metadata. Older command/job/extraction schema files remain unchanged. The workspace database schema advances to 4 because older backup implementations do not know about retained derivative files. Workspace view v3 retains its existing shape; its storage schema number now reports 4.

The immutable `ImageRegionExtractionRecord` contains job/attempt/input identity and typed digest/length references to a result JSON file, optional raster and optional TSV. It does not contain raster bytes or the word list. The result JSON contains a versioned decoder result and optional typed region recognition. `InspectImageRegionExtraction` returns this small record and the typed result after verifying the complete original-to-result chain. The `read_image_region_raster(extraction_id)` accessor returns bounded verified PGM bytes through a dedicated binary desktop command for an inert canvas display. The interface verifies the digest, dimensions and exact P5 length before allocating pixels. See the [editable design and comparison evidence](../design/IMAGE-OCR-REGIONS.md). Neither method exposes a file path or `file://` URL. There is no arbitrary completion command.

Objects live under application-managed `derivatives/objects/<sha256>`. SQLite stores a digest/length catalog, independently of semantic reference kind, so identical bytes can be referenced with different types. New files are privately staged, synced, published without replacing existing names and verified before the transaction that publishes their references and terminal job state. On Unix, retained objects must be ordinary single-link files with mode 0400; the directory is 0700. Windows uses its application-managed directory policy, rejects reparse paths and marks newly retained objects read-only. Hard-link count enforcement is currently Unix-only. Operation-time path checks do not claim protection against a malicious process with equivalent user permissions racing every filesystem operation.

Filesystem and SQLite publication are **not one atomic transaction**. A failed or crashed canonical transaction may leave complete unreferenced immutable objects. They are not exposed as results, not included in backups, and are never removed by rollback. No garbage collection or aggregate disk quota is implemented. A previously catalogued object that is missing or changed is not silently reconstructed from new output. The new job reports `derivative_unavailable`, distinguishing prior published corruption from an unreferenced target conflict. Existing immutable records remain visible only after their referenced bytes verify.

Individual bounds are inherited from the engines: original input at most 16 MiB, dimensions at most 8192, at most 12 million pixels, TSV below 2,000,000 bytes, at most 20,000 rows and 10,000 words, and bounded recognized text. Serialized result JSON is limited to 8 MiB. The inspector validates complete bounded objects in memory; it is not a streaming viewer and does not establish a workspace-wide memory ceiling.

## Backup and recovery

Before migration, the coordinator creates a complete backup. Schema 3 to 4 adds the derivative catalog without reopening reviewed findings; migrations from schemas 1/2 retain their existing review invalidation behavior. Migration changes are transactional and postconditions are checked. Newer schemas are refused.

Backup first creates a consistent SQLite snapshot. Evidence, derivative references and revision are read from that snapshot, even if another canonical writer publishes while files are copied. All referenced originals and derivative chains verify before and after copying. A bounded format-2 completion manifest is written last. Unreferenced object files are deliberately excluded. Failed backup directories may remain incomplete and cannot be restored as completed schema-4 backups.

Restore verifies the database, completion manifest, originals, catalog and every referenced chain before making a canonical destination database name visible. Files and a private pending database are copied and rechecked first; database publication does not replace an existing name. Failed restore staging may remain for diagnosis; it is not a successfully restored workspace. Existing schema-1/2/3 backups retain their previous manifest compatibility and are migrated when opened.

## Verification and remaining boundaries

`python3 scripts/test_image_region_jobs.py --runtime <app-local image-and-OCR engine root>` runs actual PNG/JPEG coordinator recognition and restore plus synthetic publication, tamper, retry, resource, cancellation and recovery cases. It records source/runtime/fixture identities, exact suite membership and collision-safe observation history; a failed run replaces the latest success projection. `test_image_region_jobs_evidence.py` tests rejected inventory, timeout, incomplete suite and same-clock history.

The ordinary Rust tests also cover missing runtime, the shared two-worker ceiling, immutable prior attempts, blank/rejected results, invalid output, cancellation, unverified exit, published-object corruption, conflicting orphan objects, Unix symlinks/hard links and outside sentinels, transaction rollback, concurrent snapshot references, and migration rollback with recovery. Schema-3 finding/report preservation is an integration test.

Actual native evidence on this host is Apple Silicon macOS development evidence. Intel Mac/Windows runtime integration, clean packaged installation, signed supported helpers, accepted word anchors, accuracy benchmarking, disk quota and crash-orphan cleanup remain unpassed. The existing experimental Mac confinement limitations remain; a successful source test is not independent security approval or completion of EW-13.
