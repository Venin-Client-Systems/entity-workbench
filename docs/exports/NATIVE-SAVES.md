# Native export preparation and verified saves

Native transaction JSON, typed-literal CSV, saved assessment HTML and retained DOCX use typed Rust operations. They do not create a Blob, initiate a WebKit download, accept frontend document bytes, choose analyst-supplied paths, or open exported HTML. The browser development interface retains its browser-owned download behavior.

## Why this path exists

Two retained macOS development-app samples (a 100,000-transaction workspace and a separate 13-row workspace) placed the main thread in WebKit's download destination callback, `SandboxExtension::createHandle`, `_sandbox_extension_issue` and `__mac_syscall`. Neither had a confirmed new download. This identifies the observed blocking boundary, not an underlying OS-permission diagnosis or a universal WebKit defect.

The pinned [Wry 0.55.1 macOS implementation](https://github.com/tauri-apps/wry/blob/wry-v0.55.1/src/wkwebview/download.rs) invokes WebKit's destination completion handler after its Rust allow callback returns. Apple's [destination delegate contract](https://developer.apple.com/documentation/webkit/wkdownloaddelegate/download(_:decidedestinationusing:suggestedfilename:completionhandler:)) starts the download when the destination is supplied; `nil` cancels it. Tauri's [DownloadEvent documentation](https://docs.rs/tauri/2.11.6/tauri/webview/enum.DownloadEvent.html) also states that the completed path is unavailable on macOS. A frontend timeout cannot repair a blocked native main-thread callback.

The desktop now refuses native webview downloads. Export commands run in Tauri's blocking-task pool, return typed small receipts, and do not enter that callback. This does not change macOS permissions, TCC, sandbox policy, Downloads, or application entitlements.

## Typed native IPC

These three dedicated native IPC functions are separate from the canonical `Command` enum. Their DOCX addition does not change workspace schema 5 or saved HTML bytes.

- `prepare_native_export(request)` accepts `transactions { request, expected_revision, expected_row_count, expected_matching }`, `html_report { report_id, expected_sha256 }`, or `docx_report { report_id, expected_document_sha256, expected_docx_sha256 }`. Transaction generation reuses `Workspace::export_transactions` exactly, including the full selected scope, matching semantics, exact amounts, row order and original verification. HTML comes exclusively from `inspect_report_snapshot` with the stored ID and digest. DOCX comes from its verified frozen artifact with both expected digests; neither is regenerated from current state.
- Preparation returns schema version 1, a random session ticket, a 120-second lifetime beginning after preparation, and a typed artifact identity. Transaction identity includes request, revision, matching profile, query digest, row count, byte length and content digest. HTML identity includes stored report ID, revision, byte length and digest. DOCX additionally binds the frozen document digest and has an exact internally derived `.docx` filename. No document bytes cross IPC.
- `commit_native_export(ticket, expected_sha256, expected_bytes)` checks the minted ticket and exact identity, verifies its private file, publishes without overwriting, and returns a saved receipt only after verification and stage cleanup. The UI checks its lifetime and currently applied scope/revision between preparation and commit. A stale or closed view discards its ticket. A commit already requested may finish while navigation changes; its file remains an explicit user-requested export.
- `discard_native_export(ticket)` removes only the matching uncommitted stage. It is idempotent after an expired/lost discard acknowledgement. A completed ticket returns its verified saved receipt and never deletes the saved file.

One export is preparing, prepared or committing at a time. At most eight small completed receipts are retained for the coordinator's lifetime. Recommit verifies the existing file and returns the same receipt. The interface retries a failed commit acknowledgement once with the same ticket. It never automatically prepares a replacement. If both acknowledgements fail, completion remains unconfirmed even if publication occurred; the content-derived filename prevents a later identical export creating duplicate files. A lost preparation acknowledgement leaves one bounded stage until expiry or shutdown.

## Storage and lifecycle

The coordinator owns `native-export-staging` and uses the existing application-managed workspace `exports` directory. JSON/HTML/CSV files are at most 256 MiB; DOCX files are at most 32 MiB. On Unix, directories are 0700 and files are created 0600. Windows files inherit the workspace's OS access controls; these checks are not application-level encryption or an AppContainer boundary.

Names are derived only from export kind, revision or report ID, and the exact SHA-256. A new stage is created exclusively, written, synced and closed. Publication uses a same-filesystem hard link that cannot clobber an existing name; an existing target is reusable only if ordinary, singly linked and byte-identical. Filesystems without the required operation fail explicitly. The temporary two-link state is allowed only when the stage and target identify the same file. The completed target must be singly linked. Unix directory synchronization precedes stage removal and acknowledgement.

Read verification rejects links, reparse points, special files, changed length, changed digest and metadata/identity changes between the named file, open handle and final named file. Unix reads use no-follow and nonblocking flags, preventing a substituted FIFO from blocking before its type check. Windows read handles allow read sharing only, and the narrow already-locked `windows-sys` adapter uses `GetFileInformationByHandle` for link count and `GetFileInformationByHandleEx(FileIdInfo)` for the complete 128-bit file identity (including ReFS). Unsupported identity queries fail explicitly. It adds no new resolved dependency package. See Microsoft's [handle-information contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle).

An exclusive preparation guard rejects concurrent generators. After acquiring it, preparation waits for the export registry, then acquires the canonical workspace; no workspace holder subsequently acquires the export registry. The expiry janitor takes only the registry, so its brief housekeeping cannot falsely reject the first preparation as a competing export. A deterministic regression holds that housekeeping lock while a first preparation waits and a second generator is rejected. Commit, discard and expiry need no workspace lock. Shutdown first requests processing cancellation, then waits for export preparation/commit to settle, joins its expiry thread and explicitly verifies staging cleanup. Cleanup failures remain errors and retain the outstanding stage; a new prepare is refused until cleanup succeeds. Drop is only a best-effort fallback. The periodic expiry task checks at most one stage. Startup, under exclusive coordinator ownership, inspects at most 32 entries and removes only ordinary files with exact canonical UUID staging names. A recognized stage left linked to a published file is safely unlinked without modifying any other link. Unknown entries, links and directories cause explicit recovery failure.

Publication and receipt creation are not a database/filesystem transaction. A crash or error after publication may leave a complete export without a receipt; it cannot create a partial named export. Saved exports are user output, not new canonical derivative references, and this slice does not add them to workspace backup manifests. Existing immutable report records remain canonical. Equivalent-user adversarial races in writable parent directories, aggregate export storage quotas and filesystem power-loss guarantees remain broader limitations; this is not a defence against a malicious user controlling the workspace.

## Verification and limits

Rust regressions cover exact bytes, immutable old HTML, stale revision, identity mismatch, single-stage bounds, expiry/discard, repeated commit/lost acknowledgement, bounded receipts, shutdown during held preparation, cleanup failure, corrupt targets/stages, symlinks, hard links, deterministic path replacement/FIFO substitution and startup recovery. Windows-specific source tests check conflicting write/delete sharing; actual Windows execution remains a separate platform gate.

`native_export_session` is a developer-only persistent transport around the real coordinator. Browser tests route native IPC into it, inspect actual files and compare complete JSON/HTML bytes with canonical results. These verify interface lifecycle and core publication, not native WebKit execution. Existing browser export, stale-scope and assessment regressions remain required. Native app verification must separately confirm a responsive UI, exact exported bytes and unchanged canonical data on the actual compiled artifact.

This slice does not reduce the existing core export's full-ledger allocation, add desktop DOCX controls, a save-location picker, or reveal/open files. The receipt displays the verified application-managed location. A future reveal operation must accept only a minted saved identity, reverify its internally derived path, and select the file without opening HTML. No product-design approval is claimed for a new layout: the existing export buttons and status text remain in use.


## Typed-literal CSV native save

The additive `transaction_csv` request accepts `request: { selection, non_accepted }`, `expected_revision`, `expected_row_count`, `expected_matching` and `expected_format: "typed_literal_v1"`. It reuses the [complete CSV serializer](../transactions/TYPED-CSV.md) with its original verification, exact decimal strings, explicit mixed-review policy, visible type prefixes and 256 MiB artifact bound. An omitted or unknown format/policy is refused; no arbitrary content or path can be supplied. Scope, row count and matching expectations are checked before a stage exists.

The prepared and saved artifact carries the complete request, captured revision, matching profile, selection hash, format name/hash, full data dictionary, row count, byte length and exact CSV digest. The native interface receives metadata only; the BOM/CRLF CSV bytes stay in Rust and the private stage. The dictionary is metadata in the receipt; it is not a second saved sidecar file. The CSV's fixed visible prefixes and the documented v1 column contract remain in the exported artifact. This does not claim ordinary numeric spreadsheet cells, Excel/LibreOffice validation or universal formula safety.

The native lifecycle schemas are additive v2 files; their older v1 bytes remain preserved. CSV prepared/saved envelopes use `schema_version: 2`. Existing JSON/HTML/DOCX envelopes remain version 1 with identical structure; the ticket and expiry behavior is unchanged. Clients must explicitly understand the new artifact kind and envelope version. The canonical Command remains v24 and the workspace schema remains unchanged.

The internally derived name is `transactions-typed-v1-r<revision>-<sha256>.csv`. An export prepared before a correction keeps its original captured bytes and revision; a fresh export after that correction has a different identity. Recommit verifies the same file and ticket, identical content reuses an existing ordinary file, and a corrupt or unrelated target prevents a saved receipt. The save does not mutate canonical transactions or reports. The selected review policy does not alter the artifact content for an identical selection, and therefore may share its filename while remaining explicit in each receipt.

Three focused Rust tests cover exact formula/leading-zero/decimal bytes through actual staging and publication, correction after preparation, exact-ticket recovery, duplicate-file avoidance, stale/count/matching/policy rejection without a stage, unknown format refusal and corrupt-target preservation. Existing lifecycle regressions continue to cover link substitution, shutdown and cleanup. The CSV desktop controls and actual native application save remain subsequent verification; this backend addition alone is not their acceptance evidence.
